02 / CONFIGURAÇÃO

Declare o que deve ser executado

Um arquivo TOML reúne limites globais, perfis de coding agents e automações. Cada automação acompanha uma fonte: issues, pull requests ou um agendamento cron.

Estrutura básica

Este exemplo configura os três tipos de automação e perfis para os quatro providers:

[settings]
max_active_tasks = 2
workspace_dir = "~/.opscli/workspaces"
state_db_path = "~/.opscli/state.sqlite3"

[coding_agents.defaults]
profile = "opencode"
timezone = "UTC"

[coding_agents.profiles.opencode]
provider = "opencode"
model = "anthropic/claude-sonnet-4"
agent = "issue-resolver"
effort = "high"

[coding_agents.profiles.codex]
provider = "codex"
model = "gpt-5.4"
agent = "work"
effort = "high"

[coding_agents.profiles.claude]
provider = "claude"
model = "sonnet"
agent = "reviewer"
effort = "high"

[coding_agents.profiles.cursor]
provider = "cursor"
model = "composer-2.5"
agent = "agent"

[coding_agents.automations.resolve-issues]
trigger_type = "issue"
repo = "acme/api"
query = "is:open label:agent-ready sort:created-asc"
profile = "opencode"
prompt = "Resolva a issue ${issue_number}: ${issue_title}\n\n${issue_body}"

[coding_agents.automations.review-pull-requests]
trigger_type = "pull_request"
repo = "acme/api"
query = "is:open label:review-needed"
profile = "claude"
prompt = "Revise o pull request ${pull_request_number}: ${pull_request_title}\n\n${pull_request_body}"

[coding_agents.automations.weekly-maintenance]
trigger_type = "cron"
repo = "acme/api"
schedule = "0 9 * * 1"
profile = "codex"
prompt = "Faça a manutenção semanal de ${repo}."

Salve o arquivo como ~/.opscli/settings.toml. Os nomes depois de profiles. e automations. são identificadores escolhidos por você; profile liga cada automação a um perfil existente. Por padrão, cada tarefa escreve em uma worktree própria, não no checkout compartilhado. O campo checkout = "main" significa usar o checkout compartilhado — não trocar para uma branch chamada main — e restaura o comportamento exclusivo anterior. O campo path continua escolhendo o checkout base.

Checkout e setup

checkout aceita "worktree" (padrão) ou "main". Worktrees usam uma branch local baseada no default branch remoto e não fazem push. Automações antigas continuam válidas, mas passam a usar worktrees se não declararem o campo.

setup_script é um caminho relativo à raiz do repositório, sem caminho absoluto nem ... Ele roda diretamente só quando o checkout base acabou de ser clonado, nunca em um checkout existente nem dentro da worktree. Assim, o que o script instala no checkout base não aparece para o agente na worktree; use checkout = "main" se o agente precisar executar onde o script escreveu. Uma falha impede o agente e remove o clone criado nesta tentativa. A validação não exige que o arquivo exista. O dry-run não busca, clona, cria worktree nem roda o script, portanto não comprova que eles funcionarão.

Watchers de issues e pull requests

Use trigger_type = "issue" ou "pull_request" e uma consulta GitHub Search em query. O campo repo usa o formato owner/repository. Prompts aceitam placeholders como ${issue_title}, ${pull_request_number} e ${repo}.

Jobs cron

Use trigger_type = "cron" e uma expressão de cinco campos em schedule. Você pode definir timezone (padrão UTC), start_date e end_date. Para exemplos completos de perfis e opções nativas, consulte Providers.

DICA

Valide antes de executar

O comando verifica o TOML sem chamar providers, criar checkouts ou gravar estado.

opscli validate
