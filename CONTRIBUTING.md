# Contributing

**Curupira** (by Caipora Labs) is the product name. The installable package, primary console script, and Python import are `curupira`. The short CLI alias is `curu`.

## Environment setup

Requirements: a Rust toolchain (see `packages/curupira-core/rust-toolchain.toml`), Python 3.11+, and
[`uv`](https://docs.astral.sh/uv/). `gh` is needed only for live GitHub discovery.
Tests use fixtures and must not call real forge or coding-agent CLIs.

```bash
uv sync --all-packages --dev
cargo test --manifest-path packages/curupira-core/Cargo.toml
```

[AGENTS.md](AGENTS.md) is the single source for verification commands, the repository
map, and security boundaries. Install the documentation tools with
`uv sync --group docs`, then preview the site with `uv run --group docs mkdocs serve -f docs/mkdocs.yml`.

## Packaging

**Maturin** builds the Rust binary (`packages/curupira-core`) into the platform wheel of
`packages/curupira-python` (`bindings = "bin"`). That wheel has no Python package
dependencies. Official triggers are one pure-Python wheel (`curupira-plugins`, depends on
`curupira-sdk`), exposed as optional extras on `curupira` (`extensions`, or forge-named
alias `github` that installs the same package).
A release is one `uv build` over all workspace members.
Console scripts `curupira` and `curu` point at the binary. Build with:

```bash
uv build --all-packages --out-dir dist
```

The Node.js extension SDK (`packages/curupira-js-sdk/`, npm
`@caipora/curupira-sdk`) is outside the uv workspace. Build and test it with
`npm install` / `npm test` in that directory.

The npm CLI (`packages/curupira-npm/`, `@caipora/curupira`) is also outside the uv
workspace. It wraps the Rust binaries; it is not a second implementation. Test it with
`npm test` in that directory. A release of `curupira` packs one optional npm package per
platform from the maturin wheel (Linux glibc and musl, macOS, and Windows, each for x64
and ARM64). Users do not compile Rust, and the installer does not download binaries from
a URL.

## Extending Curupira

See the repository map in [AGENTS.md](AGENTS.md). Curupira does not manage authentication:
provider CLIs and the user's environment do.

### Task sources (process extensions)

Official triggers live under `packages/curupira-python-plugins/` (PyPI `curupira-plugins`). Third-party
task sources speak the [extension protocol](packages/curupira-core/PROTOCOL.md) as a separate process
(`kind = "trigger"`). They discover tasks, validate configuration, and receive lifecycle
events. They must **not** build coding-agent argv, clone repositories, or manage
worktrees. See [Process extensions](docs/en/extensions.md).

### Coding agents (Rust core)

Built-in adapters live in `packages/curupira-core/src/agents/`. To add a provider:

1. Add a module under `packages/curupira-core/src/agents/` and register it on `AgentProvider`.
2. Map only documented native CLI flags; omit unset optional fields.
3. Add unit tests for argv presence/absence and a page under `docs/en/providers/`.
4. Update the README provider list and `docs/mkdocs.yml` nav alphabetically by display name.

Do not reintroduce coding agents as process extensions or Pluggy entry points.

### Git / worktrees

Clone, shared checkout, deterministic worktrees, and `setup_script` are implemented in
`packages/curupira-core/src/vcs.rs`. Extensions never perform Git operations.

## Documentation translations

Documentation is offered in English (`docs/en/`), Portuguese (`docs/pt/`), and Spanish
(`docs/es/`). Write the English page first, then update the other two **in the same pull
request**, so no language is missing detail. Every page, section, table row, and example that
exists in English must exist in `pt` and `es`.

- Translate prose and comments inside code blocks. Do not translate TOML keys, field and
  placeholder names (`${issue_title}`), commands, or program output.
- Give each heading that other pages link to an explicit id, for example
  `## Deduplication { #deduplication }`, and reuse the same id in every language so links keep
  working.
- Tables generated by macros (`triggers_table`, `agents_table`, `requirements_list`) take a
  language code: `{{ triggers_table("pt") }}`. Add the translated text to `docs/macros.py` and
  `docs/data/requirements.toml` when you add a row.
- Check with `uv run --group docs mkdocs build --strict -f docs/mkdocs.yml`.

applied on the docs theme.

## PtyTerminal manual checks

Automated tests cover the `PtyTerminal` widget with fake children (`bash -c`, `cat`,
and small Python scripts) under Textual's `run_test`. The following still need a real
machine and are not exercised in CI:

- Drive a real coding-agent CLI inside the widget (Claude Code, Codex, OpenCode, or
  Cursor) and confirm interactive input, redraw, and resize feel correct.
- Kill the Curupira host process hard (for example `SIGKILL`) while a PTY child is
  running and confirm whether an orphan remains; the widget's `atexit` hook cannot run
  in that case.
- Spot-check on macOS: `pty.fork`, window-size updates (`TIOCSWINSZ` / `SIGWINCH`), and
  process-group cleanup.

Windows is unsupported in v1; the widget should render the placeholder instead of
spawning a child.

`pyte` (LGPL-3.0) is a dynamic runtime dependency of this MIT-licensed project; it is
not vendored or statically linked. The PTY reader reads up to 1 KiB, feeds pyte in
256-byte slices under a 5 ms per-tick budget (checked before and after each feed),
then yields (`remove_reader` / `asyncio.sleep(0)` / re-add). Rendering caches Rich
styles, coalesces identical adjacent cells into one segment, rebuilds only dirty
rows into Textual strips, and refreshes those rows at about 30 fps (region refresh
so the compositor stays on the partial-update path). Scrollback uses a bounded
deque on `Screen.index` rather than `pyte.HistoryScreen` (whose per-event
`__getattribute__` wrapper dominated feed time); the deque clears on `reset` and
`resize`. When the child exits, `Process exited (N)` overlays the last content row
so it stays inside the visible height; if the child finished without a trailing
newline on that row, the overlay covers that line's text.

Re-measure with (prints per-run rows plus a min-max summary):

```bash
uv run --no-sync python scripts/measure_pty_throughput.py --seconds 20 --runs 3
```

Throughput and loop latency vary by host and load. Figures below are **min-max
across consecutive runs** of Textual `run_test` size `(120, 40)`, 20 s sample,
1 ms ticker, on Linux 6.12.94+ with Python 3.11.17 (workloads did not finish in
that window). Do not treat a single-run point as authoritative. Loop **max** is a
noisy scheduling/GC tail and is **not** a latency goal; the only hard target when
changing this path is **p99** (`yes` / `seq` < 50 ms, dense `cat` < 100 ms).

| Machine | Workload | Throughput | p99 (min-max) | max (noisy; not a goal) |
| --- | --- | --- | --- | --- |
| 4 CPUs (Intel Xeon, 15 GiB) | `yes \| head -c 50000000` | 0.345-0.371 MB/s | 16.2-17.2 ms | 30.4-173.1 ms |
| 4 CPUs | `seq 2000000` | 0.522-0.561 MB/s | 19.6-21.7 ms | 33.3-40.7 ms |
| 4 CPUs | `cat` of a 40 MiB file | 0.814-0.850 MB/s | 54.4-62.3 ms | 108.1-125.5 ms |
| 8 CPUs (Linux 6.12.94, Python 3.11.17) | `yes \| head -c 50000000` | 0.258-0.277 MB/s | 18.6-20.0 ms | 33.7-328.6 ms |
| 8 CPUs | `seq 2000000` | 0.346-0.374 MB/s | 26.3-28.3 ms | 47.1-67.3 ms |
| 8 CPUs | `cat` of a 40 MiB file | 0.505-0.619 MB/s | 76.1-82.6 ms | 164.0-221.5 ms |

Envelope across both machines (do not document a narrower band than this without
re-measuring both): `yes` 0.258-0.371 MB/s (p99 16.2-20.0 ms), `seq`
0.346-0.561 MB/s (p99 19.6-28.3 ms), `cat` 0.505-0.850 MB/s (p99 54.4-82.6 ms).
Automated tests cover the `yes` flood (p99 < 50 ms); a denser `cat`-style flood
was flaky under CPU load, so it stays as a measurement-script workload only.

Update these ranges when changing the reader or render path (re-run with
`--runs 3` on each class of machine you care about and widen the table).

### PtyTerminal lifecycle caveats (documented, not changed)

- If the Curupira host is killed with `SIGKILL`, the widget's `atexit` / `on_unmount`
  cleanup does not run. A child that ignores `SIGHUP`, and any grandchildren, can
  survive and be reparented (typically to PID 1).
- Grandchildren that call `setsid` leave the child's process group; force-shutdown
  only signals the child's process group, so those session leaders survive until a
  clean host close or an external kill.
- `_shutdown_child` (unmount / restart / atexit) may block the event loop for up to
  about 0.1 s (`_KILL_GRACE_SECONDS`) between `SIGHUP` and `SIGKILL` while polling
  `waitpid`.
- Outbound PTY writes buffer on `EAGAIN` and retry via `loop.add_writer` (bounded to
  1 MiB); older builds discarded the remainder of the buffer on `EAGAIN`.

## Dependency audits

`pip-audit` runs in CI against the synced development environment:

```bash
uv run pip-audit
```

Investigate every finding: upgrade the affected constraint in `pyproject.toml`,
re-sync the lockfile, and re-run the full verification suite. If a finding is not
exploitable in this project (for example, a dev-only tool with no network path to
untrusted input), document the reason in the pull request instead of adding a
permanent ignore.

## Releases

Each package has its own version and is released by its own git tag,
`publish/<project>/<version>`, where `<project>` is `curupira`, `curupira-sdk`, or
`curupira-plugins`, and `<version>` is a PEP 440 version such as `0.3.0dev0`. The tag is
the only source of a release version, and [AGENTS.md](AGENTS.md#versions) lists how each
package reads it:

- `curupira-sdk` and `curupira-plugins` read the tag through hatch-vcs.
- `curupira` takes its version from the Rust crate's `Cargo.toml`, which the release
  workflow stamps from the tag before building. The Rust crate, the npm CLI manifest, and
  the plugin manifest cannot read git, so their checked-in versions are placeholders.
  `@caipora/curupira` is released by the `curupira` tag, using the Cargo semver form of
  that version. It is not a fourth project name in the tag.

One workflow, `.github/workflows/publish.yml`, releases every project: it resolves the tag,
builds all distributions, verifies the tagged project's versions, publishes it to PyPI
(environment `pypi`, Trusted Publishing), and attaches a GitHub Release for stable
versions only. A `publish/curupira/<version>` tag also packs the npm CLI and its platform
packages from those wheels, smoke-tests each native binary, installs the Linux x64
tarball, and publishes them to npm (environment `npm`, Trusted Publishing) before the
GitHub Release. `workflow_dispatch` rehearses the build and does not publish. Before
anything is uploaded, the tag must name a known project, the distributions of that
project must carry the tag's version (`verify_dist_version.py`, and the npm tarball
check in `publish.yml`), and the commit must have green CI (`require_ci_checks.py`).

### Cutting a release

1. Make sure CI is green on the commit to release. Run the verification suite from
   [AGENTS.md](AGENTS.md) and `packages/curupira-python/scripts/check_packaged_readme.py`.
2. Move the `Unreleased` entries in `CHANGELOG.md` into a version section if the release
   needs one.
3. Tag the commit and push the tag:

```bash
git tag publish/curupira-sdk/0.1.0dev0
git push origin publish/curupira-sdk/0.1.0dev0
```

Publish in dependency order: `curupira-sdk`, then `curupira-plugins` (it depends on the SDK),
then `curupira` (its extras depend on `curupira-plugins`). PyPI never accepts the same file
twice, so a fix needs a new version.

### Trusted Publishing

PyPI accepts an upload only from a trusted publisher registered for the project: owner
`caipora-labs`, repository `curupira`, workflow `publish.yml`, and environment `pypi`. A
project that does not exist on PyPI yet, such as `curupira-sdk` before its first release,
must be registered as a pending publisher with those values before its tag is pushed.

npm accepts `@caipora/curupira` and each `@caipora/curupira-<platform>` package from the
same workflow and the `npm` environment. Register a trusted publisher for every package
before the first `publish/curupira/<version>` tag. Platform packages are published
first, then the CLI that depends on them.
